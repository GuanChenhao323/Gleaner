## 1. 目标与非目标

### 目标

- 插件一次保存同页多条事项，每条有独立身份，逐条返回结果，部分失败如实报告。
- 事项按待办、日程、通知三类管理，各有对应的处理状态，可按类型和状态筛选。
- 用户修改与来源版本分开保存；来源更新不覆盖用户修改，冲突时两边都保留并标出。
- 每条事项记录是否支持、是否启用监测、最后成功检查时间和最近结果；插件可领取监测任务并回报结果。
- LLM 默认关闭，需显式打开。

### 非目标

- 插件页面识别、各页面 `locator` 取法与后台调度（插件负责人；Spike 01／02）。
- 分类规则的质量（分类负责人）。本包只提供可替换的默认规则。
- Flutter 界面改造（工作台负责人）；本包保证接口和旧客户端兼容。
- 订阅来源（RSS、网页、Moodle Web Service、邮箱）的采集方式不变，属于课程技术交付。

## 2. 数据流

### 改动前

```text
插件 → POST /api/clips {url,title,text} → 每人一个 clip 来源，身份键 clip:<url> → items（单条）
items.kind 七种渠道类型；user_item_state 只有已读、待办、收藏、隐藏、备注、截止覆盖
clip 事项保存后不再检查；监测只按来源进行
```

### 改动后

```text
插件 → POST /api/captures {page, items[]} → 逐条：身份键 capture:<url>#<locator> → Pipeline → items(+item_type) → 逐条结果
                                                                       └→ item_monitors（supported 时启用）
插件后台 → GET /api/monitor/due → 重新获取页面 → POST /api/monitor/results → Pipeline 比较、记版本 → item_monitors
工作台 → GET /api/feed?type&status、GET /api/items/{id}（生效值 + fields + conflicts + monitor）
       → PATCH /fields、POST /fields/resolve → user_item_edits（来源更新从不写这里）
       → PUT /state {archived, done}、PUT /monitor {enabled}
```

### 自然语言说明

旧实现把网址当事项身份，同一页面的多条内容互相覆盖；类型只有渠道之分；用户只能改截止时间和备注；插件保存的事项不会再被检查。本包把身份细化到页内定位符，批量接口逐条走原有流水线，因此去重、版本、推送都沿用现有逻辑。类型和状态在事项与个人状态表上各加一列。用户修改单独建表，并记下修改时的来源值，读取时比较得出生效值和冲突，来源侧代码不需要知道用户改过什么。监测结果由插件回报，复用流水线的比较逻辑；失败只更新失败信息，不碰最后成功时间。

## 4. 检验清单

[ ] 同一页面两条事项（不同 locator）保存为两条记录；同一 locator 再保存不新建，内容变了 version + 1
[ ] 一批里一条字段不合法，其余照常保存，顶层 ok 为 false，failed = 1
[ ] page.url 非法、items 为空或超过 50 条、locator 重复：整批 422，什么都没保存
[ ] 未登录 401；旧 /api/clips 照常可用
[ ] 插件给出的类型优先；缺省时按默认规则；旧数据 assignment 回填为 todo
[ ] 三类状态：done、read、archived 分别生效；feed 按 type、status 筛选正确
[ ] 修改标题后来源更新标题：items 改了，生效值仍是用户的，conflict 为 true；resolve mine／source 各自正确
[ ] reset 恢复来源值；null 截止时间与“未修改”区分；旧 deadline_override 仍生效
[ ] supported 的事项默认启用；unsupported 的事项开启监测返回 409
[ ] monitor/due 只发到期且启用的事项，租期内不重复发
[ ] 回报成功无变化：unchanged，last_success_at 更新；内容变化：changed，记新版本
[ ] 回报失败（auth_expired）：failed，last_success_at 不变，不显示 unchanged
[ ] 迁移在已有数据的库上执行成功；SQLite 与 PostgreSQL 都通过
[ ] 未设置 GLEANER_LLM_ENABLED 时即使配齐三项也不调用模型
[ ] 粘包、畸形输入：非 JSON、字段类型错误、超长字符串都返回 4xx 而不是 500
[ ] ruff check、ruff format --check、全量 pytest 通过
