# Campus Radar｜产品定义与 MVP 需求基线

> 版本：V1.8（2026-11-15，单弹窗采用雾白浅色布局）
>
> 文档性质：产品需求基线；当前产品范围的唯一权威来源；已取代旧提案中的产品范围，技术可行性与实际交付状态另行验证。
>
> 适用范围：第一版 MVP 的产品目标、功能范围、验收依据及后续扩展方向。

## 0. 一句话产品定位

**Campus Radar 是一款面向本校学生的校园信息管理应用，通过 Chrome 插件按条件提取普通网页的当前 DOM 片段，并对 Moodle 和指定校园网页提供专用提取规则，自动结构化为可管理的个人事项，并在 Flutter 工作台中跟踪处理状态与来源变化，降低信息整理、事务跟踪和重复核对的成本。**

### 2026-11-14 用户确认的来源与读取交互

本节规定当前主流程；未被本节改变的模块职责与需求保留。

- 登录 Campus Radar 后提供三个真实来源入口：学院公告／学生系统、教师信息、Moodle 课程与作业。入口存在不代表账号已连接、已有事项或后台可访问；本地模拟订阅应单独说明。
- 学生系统与 Moodle 由学生分别在原站登录；教师信息是指定的公开人员网页，无需学生登录。不在 Campus Radar 中输入学校密码。
- 学生首页登录后即可预览当前公告／资讯；进一步查看通过实际的资讯列表与详情链接。独立课表页面与首页“我的日程”分开；只读取当前课表视图，不把缺少日历映射的学期／周次推算为日期。
- 交互为来源入口 → 原站登录 → 打开插件直接输入条件 → 只抓取当前页匹配内容 → 预览整组结果 → 一次保存 → Flutter 管理。无需先全量抓取再逐项勾选；修改条件使旧结果失效。
- 保存方式已确认：先预览匹配结果，再点一次保存全部匹配项。零匹配不回退整页；同名课程仅确认课程范围；摘要／身份不足只预览。支持基础课程名、标题关键词、人员字段和明确的结构化条件；复杂语义规则、历史范围和自动监测条件仍待决。当前新读取保存快照，不自动监测。

普通课程名／关键词（例如“人工智能”）预览当前页相关卡片、匹配标题及已加载内容；“某课程的作业”限定为作业；“Timeline”逐条预览已加载活动，保留所属课程原文、日期／时间原文、链接和原文对照；“Moodle Support”独立作为联系信息预览，支持指定邮箱等字段。课程概览与原生关联明确的作业分组，活动主标题不拼接课程上下文或图标类型。无法确认原生课程归属时不可凭课程名称子串绑定。不自动进入其他页面。课程卡片只有名称、链接、进度时只供预览，用户进入详情后才保存；附件只有名称与链接时不视为已读取文件正文。未识别页面结构、需进入详情和真正零匹配必须分开提示。

实现与实际验收分开记录，见 [读取契约](architecture/page-extraction-v1.md) 和 [插件说明](browser-extension.md)。

## 1. 为什么做：用户问题与产品目标

### 1.1 目标用户

本校在读学生，优先考虑需要频繁处理 Moodle、学院公告等多个来源信息的学生。

### 1.2 核心用户问题

学生收到信息后，往往不会立即处理；之后可能忘记任务、难以判断是否已完成，或需要返回原始网页检查通知要求是否变化。

| 用户成本 | 典型行为 | 期望改善 |
| --- | --- | --- |
| 信息整理成本 | 阅读通知后，手动记录标题、时间、要求和链接 | 一次选择，自动结构化并保存 |
| 事务管理成本 | 靠记忆、截图或分散笔记追踪完成情况 | 在统一工作台查看、编辑和更新处理状态 |
| 信息核对成本 | 反复打开原网页核实内容是否修改 | 保存来源和历史版本，对支持的来源主动检查变化 |

### 1.3 产品目标

1. 降低「发现一条有价值的校园信息 → 建立一条可管理记录」的操作成本。
2. 让学生可以在 Flutter 工作台集中查看不同类型的信息，并持续跟踪个人处理状态。
3. 保留信息来源和采集快照；在支持监测的情况下，主动发现原始信息的变化。
4. 在有限的本校真实场景中交付可重复演示、可验证的端到端用户闭环。

**尚待验证的假设：** 学生存在持续、重复的信息整理与核对需求；本产品的流程比现有 Moodle、日历和待办工具更省时。不能将其视为已经得到用户研究证明的事实。

## 2. 做成什么：产品形态与核心使用流程

### 2.1 产品组成

| 组件 | 产品职责 |
| --- | --- |
| Chrome 浏览器插件 | 在普通 HTTP(S) 网页按用户先输入的字面条件提取匹配片段，校园专用规则保留；预览后一次保存 |
| 本地后端 | 接收插件请求；配合插件完成程序化结构化与分类；处理去重、持久化、来源版本及变化监测。LLM 为效果不足时的候选方案，见第 2.5 节 |
| Flutter 信息管理客户端（工作台） | 按类型展示信息；查看详情、修改字段与处理状态、查看来源和更新提示 |

**客户端是 Flutter 应用，不应写为“Web 工作台”。** Flutter 第一版具体交付的操作系统平台（桌面／移动端）尚待团队确认；多端数据同步属于 P2，与 Flutter 的跨平台 UI 能力分开定义。

### 2.2 核心用户闭环

1. 学生打开普通 HTTP(S) 网页，或本校 Moodle／指定校园网页。
2. 用户在插件中输入课程名或关键词；插件先定位范围，只提取匹配的通知或事项。
3. 用户点击保存；插件经约定的接口将所选内容发送至本地后端。
4. 系统自动理解内容、提取适用字段、分类，识别已有记录或新增记录，并持久化。用户无需手动逐项录入。
5. 学生通过 Flutter 工作台查看、筛选、编辑和管理处理状态，必要时打开原始链接。
6. 对明确支持监测且已启用监测的来源，系统在运行条件满足时定期检查；发现实质变化后记录版本并提示。

### 2.3 信息类型和处理语义

| 信息类型 | 例子 | 主要字段 | V1 处理状态 |
| --- | --- | --- | --- |
| 待办任务 | 作业、报名、材料提交 | 要求、截止日期、来源 | 待完成／已完成 |
| 日程活动 | 讲座、考试、校园活动 | 时间、地点、描述、来源 | 未归档／已归档 |
| 普通通知 | 学院公告、教学调整 | 摘要、正文、来源 | 未读／已读 |

字段可以缺失；无法确定的日期必须保留为空或待确认，不能编造。允许用户修正系统提取结果。

### 2.4 统一术语

| 术语 | 定义 |
| --- | --- |
| Campus Radar | 当前产品名称；Gleaner／拾课是仓库及历史实现名称，代码包、配置键和协议标识暂不改名 |
| 来源 | 事项的出处及重新获取所需的定位信息；一个来源页面可以包含多个事项 |
| 候选信息 | 插件在受支持页面识别出的内容单元；只有用户条件匹配且预览后明确确认的结果才进入保存流程 |
| 事项／记录 | 保存后可管理的个人信息单元，统一分为待办任务、日程活动、普通通知；“事务”沿用同一含义，不另建实体 |
| 采集快照 | 某次成功读取的来源原始内容及采集时间 |
| 来源版本 | 同一事项的来源内容发生实质变化后形成的历史版本；重复读取不等于新版本 |
| 用户修改 | 用户对提取字段的修正，与来源版本及个人处理状态分别记录；来源更新不得静默覆盖用户修改 |
| 监测 | 对已保存且支持、启用监测的事项重新获取来源并比较；不承诺发现未保存的新通知 |

“查看”是操作；日程的持久化状态为未归档／已归档。来源变化与用户修改发生冲突时，应保留两者并提示确认；字段合并细节在实施前明确。

### 2.5 结构化实现选择

- P0 要求自动提取字段和分类。首先使用浏览器插件获取页面结构、正文和可用元数据，配合程序规则及解析完成处理。
- 在约定样例上评估分类、日期、要求等字段的正确性、缺失情况和用户修正成本；质量阈值在验证阶段确定。
- 只有插件与程序无法取得可接受结果时，才考虑 LLM；记录规则方案不足的样例、候选方案收益、成本与失败处理，再确定是否采用。
- LLM 不属于必选技术，也不作为单独的 P0 功能或默认外部依赖；具备模型配置不代表应自动启用。若采用，需明确发送内容范围、隐私处理和失败反馈。
- 缺失或不确定字段保持为空或待确认，允许用户修正；任何实现都必须满足相同的用户验收标准。

## 3. MVP 是什么：第一版功能范围

**MVP 定义：** 在本校 Moodle 与少量指定网页中，完成「选择采集 → 自动结构化 → 保存与管理 → 来源追溯 → 对可监测来源发现变化」的完整闭环。

### 3.1 功能优先级

| 编号 | 优先级 | 功能 | 第一版要求 / 规划 |
| --- | --- | --- | --- |
| F01 | P0 | 按条件采集与预览保存 | 弹窗输入条件，先定位范围再提取匹配内容，预览后一次保存；零匹配不回退全量 |
| F02 | P0 | 插件与本地后端通信 | 请求、结果与异常反馈明确 |
| F03 | P0 | 自动结构化提取与分类 | 优先由插件与程序提取适用字段、识别三种类型；效果不足时评估 LLM；不能虚构缺失信息 |
| F04 | P0 | 信息保存、编辑、持久化 | 可修改字段，重启后数据仍保留 |
| F05 | P0 | 分类展示与状态管理 | Flutter 工作台支持按类型、状态查看与操作 |
| F06 | P0 | 来源追溯与基础去重 | 保存原始链接；重复采集不直接产生重复事务 |
| F07 | P0 | 周期性主动变化监测 | 只监测已保存且可监测的来源，运行边界见第 4 节 |
| F08 | P0 | 内容变化记录与提示 | 记录版本，突出实质内容或截止日期变化 |
| F09 | P0 | 监测状态与异常反馈 | 显示最后成功检查时间，区分变化、无变化与失败 |
| F10 | P1 | 高级搜索与复杂筛选 | 多条件查找历史信息 |
| F11 | P1 | 截止日期提醒 | 临近截止时提醒学生 |
| F12 | P1 | 自定义监测策略 | 用户可进一步设置频率、关注规则等 |
| F13 | P2 | 多端同步 | 跨设备同步记录及处理状态 |
| F14 | P0 | 通用 DOM 网页片段 | 普通 HTTP(S) 当前已加载 DOM 按字面条件提取、弹窗内预览、整组资料明确保存；校园规则增强；不可读取类型明确说明 |
| F15 | P2 | 个性化分类与自动化规则 | 依据用户偏好进行更灵活的信息管理 |

P0 为必须满足的第一版产品能力；P1 为时间允许时增加；P2 为未来规划。P0 的“主动监测”可以只覆盖明确列出的可验证来源，不能推定所有已支持采集的网页都可自动监测。

### 3.2 首版来源范围

- 本校 Moodle 的指定页面类型（以实际适配与测试结果为准）。
- 少量经过明确列名、授权和适配的校园网页。
- 通用提取不依赖站点白名单；不承诺读取浏览器受限页、未加载／嵌入／关闭 Shadow DOM、图片画布或完整学校邮箱。
- 应在开发任务中补充**具体 URL 类型、页面结构、适配负责人和测试样例**。

## 4. 主动变化监测：能力与边界

### 4.1 已确认运行模式（方案 A）

- Chrome 正在运行、相关扩展正常启用且本地后端可用时，系统定期尝试检查已保存的信息来源。
- 默认仅检查**已保存、允许监测、可重新获取**的来源；采集能力与监测能力分别判断。
- Chrome 关闭、设备休眠或本地后端不可用时，**不保证持续检查**。
- 运行环境恢复后，监测任务应能够继续；已错过的检查周期不承诺逐次补跑。
- V1 不承诺 24 小时监测、实时发现或秒级推送。
- 具体检查间隔和调度实现，须在技术验证后确定；用户看到的是**最后成功检查时间**，不能把一次未执行或失败的检查显示成“无变化”。

### 4.2 检查结果应如何表达

| 状态 | 含义 | 对用户的反馈 |
| --- | --- | --- |
| 无变化 | 成功重新获取，相关内容未发现变化 | 更新最后成功检查时间 |
| 发现变化 | 成功重新获取，相关内容发生实质改变 | 保留版本，展示变化提示与差异 |
| 检查失败 | 网络错误、认证过期、权限不足或解析失败 | 记录失败原因，不更新为“无变化” |
| 暂不支持监测 | 当前来源没有可靠的自动获取方案 | 明确提示，仅保留原始来源和手动采集能力 |

### 4.3 检测质量边界

- 比较与用户保存事项相关的正文、要求、时间等内容，避免页面广告、导航栏、时间戳等无关变化触发误报。
- 原始通知发生变化，应与已有事项建立版本关联，避免直接新增重复记录。
- 对登录后可访问的 Moodle 页面，是否能在关闭目标标签页后重新读取，需要实测；不得仅凭“浏览器中能看到”推断后台可访问。
- 涉及实际学校系统的自动访问，应符合仓库中现有的授权、访问频率和隐私约束。

## 5. P0 用户故事与验收标准

用户故事采用「作为学生，我希望……，以便……」；验收标准描述可重复验证的行为。

### 5.1 信息采集与结构化

| 编号 | 用户故事 | 验收标准 |
| --- | --- | --- |
| US01 | 我希望先输入想抓取的内容，避免逐条选择整页信息。 | 三课程面板输入目标课程，只预览该课两条作业；其余课程正文不提取或提交；一次保存匹配结果；改词、歧义和零匹配明确反馈。 |
| US02 | 我希望一键保存选中内容，以便避免手工填写。 | 插件将内容发给本地后端；收到成功响应后显示成功；后端不可用时正确报错，不虚报保存成功。 |
| US03 | 我希望系统自动理解内容，以便形成结构化记录。 | 对测试样例识别待办、日程、通知三类；提取标题、摘要、适用的时间和要求；未知字段保持为空，不编造截止日期。 |

### 5.2 信息管理

| 编号 | 用户故事 | 验收标准 |
| --- | --- | --- |
| US04 | 我希望信息自动保存，以便之后继续处理。 | 保存结构化内容、原文、来源 URL、采集时间；用户可编辑字段；重启本地后端后记录仍存在。 |
| US05 | 我希望跟踪不同事项的处理状态，以便了解进度。 | 待办支持待完成／已完成，通知支持未读／已读，日程支持查看详情及未归档／已归档状态；工作台可按类型及状态筛选。 |
| US06 | 我希望查看原信息，以便核对要求。 | 记录可打开原始来源；重复采集同一来源事项时，不直接创建重复记录；同一 URL 里多个事项仍可区分。 |

### 5.3 主动变化监测

| 编号 | 用户故事 | 验收标准 |
| --- | --- | --- |
| US07 | 我希望系统自动检查已保存来源，以便减少重复访问。 | 对已启用且支持监测的来源，在 Chrome 和后端运行时能周期检查；无需用户保持原网页标签页打开；恢复运行后继续检查。 |
| US08 | 我希望知道原通知发生了什么变化，以便调整安排。 | 修改受监测测试通知的正文或截止时间后，在下一次**成功**检查时可发现实质变化；保留新旧版本；Flutter 工作台可查看差异。 |
| US09 | 我希望确认监测是否正常，以免误判信息未变。 | 显示最后成功检查时间；区分无变化、已变化、失败、暂不支持；登录过期或网络错误不标为“无变化”。 |

> 验收时应分别测试成功路径与错误路径；无论采用程序规则还是候选 LLM，都必须验证字段正确性和用户可用性，输出格式合法不代表提取结果正确。

## 6. 最小数据需求

| 类别 | 必要数据 |
| --- | --- |
| 身份 | 记录 ID、信息源标识、来源内事项标识（若有） |
| 内容 | 标题、摘要、信息类型、原始内容、结构化字段 |
| 事务 | 截止或活动时间、处理状态、用户编辑结果 |
| 来源 | 来源 URL、平台、采集时间 |
| 监测 | 是否支持、是否启用、最后成功检查时间、检查结果／错误 |
| 版本 | 当前版本、历史快照或版本引用、更新时间、可用于比较的内容摘要 |

**数据建模要求：** 一个网页可能包含多条事项，不能简单把 URL 作为事项的唯一 ID；重新采集、版本变化和用户手动修改之间的关系，需要在数据模型中明确区分。此处定义逻辑数据需求，暂不规定具体数据库表结构。

## 7. MVP 端到端验收场景

### 场景 A：从网页生成事务

1. 打开指定 Moodle 测试页面。
2. 用户输入目标课程条件，插件只提取该课程两条匹配内容，排除其他课程。
3. 用户核对预览，一次保存两条；无需逐条勾选。
4. 后端自动结构化、分类、去重并保存。
5. Flutter 工作台正确显示两条记录及来源。

### 场景 B：主动发现信息变化

1. 保存一条已确认支持监测的测试通知并启用监测。
2. 在测试来源修改正文或截止日期。
3. 保持 Chrome 和本地后端运行，触发下一次定期检查。
4. 工作台显示原事项的变化提示、新旧版本及差异。
5. 模拟网络错误或会话失效，确认不会把失败显示成“无变化”。

### 场景 C：管理与追溯事务

1. 在 Flutter 工作台筛选未完成事项。
2. 打开记录详情并修改某字段。
3. 将一项任务标记为已完成。
4. 重新打开客户端，确认内容和状态仍保留。
5. 点击原始来源链接，返回对应通知页面。

**MVP 完成标准：** 以上三条场景均可在约定的本地测试环境稳定复现，错误路径有清晰反馈，所承诺支持的真实 Moodle 页面类型另经授权验证。三个场景通过不自动等于所有 Moodle 页面均已支持。


### 通用网页资料（2026-11-14 用户确认）

2026-11-15 用户确认：使用工具栏插件的单弹窗采集面板，采用520px加宽、固定浅色的雾白布局；原文就地展开、长内容在面板内滚动。连接状态／设置、当前网页、提取条件、匹配预览、保存反馈均在同一框内完成；移除独立双栏预览页。匹配位置直接展示，原片段与依据按需展开。来源声明在存在可保存片段后出现，私人标签输入后须明确确认。最近记录在弹窗内恢复，历史内容标记来源，不覆盖当前未提交输入。只有后端严格确认后显示成功，未确认或需重新登录时保留原预览和请求。

输入字面关键词／短语，可选择正文与列表或仅标题。先提取、核对匹配片段与依据，再明确保存；不先列出整页信息让用户逐条筛选。不使用 AX、OCR 或 LLM 解释采集条件。

普通网页片段／列表摘要可保存为网页资料快照，明确不是完整文章／邮件。整组匹配作为一份资料，由同工作台 owner、用户声明来源标签、完整 URL、条件和范围确定；再次明确保存更新资料版本。每个片段不被伪造为原生独立事项。私人来源填写标签，公开网页由用户明确选择；标签不是网站登录认证，切换账号时须换标签。请求重试幂等，零匹配不能清空旧资料，不自动监测。Moodle 等校园原生事项身份及摘要只预览政策不因此改变。

实现契约：[IC-WEB-CAPTURE-001](architecture/universal-web-capture-v1.md)。本需求扩大原先 F14 的当前阶段范围，不将“任意网站”解释成所有技术类型均可读取；实际测试与限制见插件说明。

## 8. 明确边界与暂不交付内容

### 8.1 V1 必须遵守的边界

- 通用能力覆盖普通 HTTP(S) 当前已加载、可读取的 DOM；校园适配器保留账号／身份／完整度限制，不以通用回退绕过。
- 用户主动选择需要保存的信息；不承诺自动发现所有尚未浏览的新通知。
- 仅对支持监测的已保存来源主动检查；监测条件以 Chrome 运行且本地后端可用为前提。
- Flutter 承担应用 UI；具体首发桌面／移动平台尚未定案。
- 数据本地持久化；跨设备状态同步放在 P2。
- 不要求学生手动录入每个结构化字段，但允许事后修正。

### 8.2 不属于本次 P0 交付承诺

- 全天候云端监测与秒级推送。
- 任意页面类型的完整覆盖、未浏览内容自动接入、邮件 API 接入或全天候监测。
- 云账户、多用户多端同步与跨设备状态一致性。
- 个性化推荐、复杂自动化规则。
- 高级搜索、截止提醒、自定义监测策略（分别列为 P1）。

## 9. 技术可行性验证与尚待决策

### 9.1 开发前必须验证的两个问题

| 验证项 | 需要证明的事实 | 失败时的处置 |
| --- | --- | --- |
| Spike 01 · 插件采集 | 指定 Moodle 页面能识别多条候选信息，选中内容可稳定传到本地后端 | 缩小页面类型或简化选取方式；不虚报通用支持 |
| Spike 02 · 主动监测 | 关闭 Moodle 目标标签页但保持 Chrome 运行时，可以重新获取**受支持**的已保存通知并检测人为修改 | 缩小可监测来源范围，研究授权接口／登录会话方案，不能静默降低错误提示要求 |

开发和 CI 只使用模拟校园数据；接入真实学校系统的授权、账号与速率要求遵循仓库现有 `CLAUDE.md` 与 `docs/integrations/` 约定。

### 9.2 尚待补充的关键决策

1. 指定校园网页的准确清单、所支持页面类型及验收样例。
2. Flutter V1 首发平台（Windows/macOS 桌面，或其他平台组合）。
3. Moodle 后台重新读取的授权与认证策略；监测频率及失败重试政策。
4. 程序化提取与分类的测试集、可接受质量阈值和人工修正策略；仅在效果不足时评估是否引入 LLM。
5. 量化用户价值的方法：相对手动整理的操作次数、耗时、任务管理完成率与变化检测误报率；具体目标由需求验证阶段确定。
