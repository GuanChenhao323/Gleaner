# 拾课 Gleaner：面向学生的个性化信息聚合工作台 — 项目提案

Oct 21, 2026 · @Andy

## 摘要

**拾课**（英文名 Gleaner）是一个面向学生的个性化信息聚合工作台。英文名取自 glean 的原意——在收割后的田里拾取散落的麦穗，正如把散落在各个渠道的课程信息拾起来、整理好。学生订阅 Moodle 课程页面、学院通知和学校邮箱后，系统定期检查并提取内容：作业整理成列表和日历，通知转成带精简标题、摘要和原文链接的收件箱消息，重要变更会被突出显示。

它要解决的不是“信息没有发布”，而是“信息发布了，学生却没及时看到、没理解、没放进自己的安排”。平台支持离线查看缓存，恢复连接后自动同步新增内容和变化；同一事项被修改时，更新原有记录，而不是再多一条通知。

项目的技术核心是一个**多协议信息接入与推送网关**。我们从 socket 层自研 HTTP/1.1 网关、WebSocket 推送、MQTT 通知、IMAP/SMTP/POP3 邮件客户端、事件驱动采集引擎和节点间二进制协议，并部署上线供本校同学使用。

老师已确认按 **等级5（系数1.30）** 认定，依据是参考表中的“多协议网关（HTTP + WebSocket + MQTT）”“已上线部署服务（有真实用户）”和“高并发压测与优化”三项（见“难度定级依据”）。

## 背景与动机

### 一个周日晚上的场景

一位同学在周日晚上安排下一周的学习任务：先登录 Moodle，逐门课程查看作业要求和截止时间；再打开学院网站筛选近期通知；最后把相关事项手动记进日历。这个过程中常遇到五个问题：

| 痛点 | 具体表现 |
| --- | --- |
| 作业提醒没及时看到 | Moodle 发了提醒邮件，但邮件被其他消息淹没，直到再进课程页才发现任务 |
| 多门课截止时间难统筹 | 每门课各自展示作业，需要逐项查找、手动汇总，容易遗漏，或临近截止才发现任务扎堆 |
| 已记录的要求发生变化 | 老师调整截止时间、替换附件或补充要求后，个人日历和笔记仍是旧信息 |
| 是否相关要逐条判断 | 学校资讯面向不同年级和专业，要打开正文甚至附件才知道自己是否符合条件 |
| 看过的信息不易再找到 | 感兴趣的活动暂时没处理，等要报名时又得回网站或邮箱翻找原通知和入口 |

这些问题说明：信息已经发布或发送，不等于学生及时看到、理解了，更不等于它已经进入个人安排。

### 我们要做什么

减少学生重复查阅、筛选和整理信息的成本：打开工作台就能看到与自己有关的新增事项、最新要求和时间安排，并清楚每条信息的来源和有效性——来自哪里，最后一次成功检查是什么时候。

### 为什么这是一个网络编程问题

校园信息聚合的难点几乎都在网络层，界面只是最后一个出口：

- **协议异构**：Moodle 和学院网站走 HTTPS，学校邮箱收信走 IMAP/POP3、发信走 SMTP；推送端还需要 WebSocket 和 MQTT。
- **会话与认证**：需要登录的来源要保存并复用 Cookie 或 Token，识别会话过期并提示重新登录。
- **高并发采集**：多用户、多信息源要定时检查，必须用事件驱动 I/O、连接复用和按主机限速，而不是一个源一个线程。
- **实时与可靠**：新增和变更要秒级到达；网络抖动、节点宕机时要超时、重试、故障转移，做到不丢不重。
- **离线与增量同步**：客户端恢复连接后，要按同步游标补齐期间的新增和变化，并保证离线时的操作不会重复生效。

### 项目目标

以下为目标值，将在第 4 周首轮基准测试后校准。

1. 接入 4 类校园信息源：Moodle 课程页面、学院通知网站、学校邮箱、学校官网教师信息。
2. 作业自动汇总为跨课程的列表和日历；原通知修改后，同一事项在一个检查周期内更新并标出变化。
3. 新信息入库后推送到在线客户端，延迟 P99 < 1 秒。
4. 单个推送节点支撑 ≥ 5,000 个并发 WebSocket 长连接；节点宕机后客户端 10 秒内恢复，消息零丢失。
5. 客户端离线时可阅读缓存；恢复连接后补齐仍可获取的新增和变化，已读、收藏、待办状态不丢失。
6. 部署上线，学期内获得 ≥ 50 名真实注册用户。

## 竞品分析与定位

现有产品已经很好地解决了网页变化监测和结构化采集。我们不与它们比拼通用能力，而是聚焦校园场景：把监测结果变成持续维护的作业、通知和日程。

### 不能忽略的替代方案

Moodle 本身提供 Timeline 和 Calendar，可以汇总课程截止事项；学校邮件、课程群和个人日历也已融入学生习惯。因此“只能逐门课查看截止日期”不能当作未经验证的事实。本校是否启用这些功能、老师是否完整填写截止字段，需要在第 1–2 周实地确认。

本项目要解决的是现有渠道剩下的问题：

- Moodle 之外的学院通知，是否仍需分开查看；
- 提醒邮件的信息是否足够，还是要逐条回原页面核对；
- 同一事项跨渠道出现时，是否造成重复阅读和版本混淆；
- 个人日历中的记录，是否需要手动跟随原通知更新。

### 定位

面向学生的校园信息整理与使用体验：在已授权的信息源中持续获取内容，把它们组织成有来源、可理解、可安排的个人事项，减少跨渠道查阅和手动整理。

三个设计目标需要通过用户验证来证明，而不是预设已优于竞品：

1. **减少配置**：无需研究网页规则，用校园模板即可接入典型信息源。
2. **减少整理**：作业、通知和日期自动进入合适的视图。
3. **减少重复核对**：同一事项的新增、修改和个人处理状态始终关联在一起。

## 目标用户与使用场景

核心用户是本校在读学生，优先服务课程多、信息源分散的人群。

| 用户画像 | 特点 | 最需要的功能 |
| --- | --- | --- |
| 大一新生小林 | 不熟悉 Moodle 和学院网站，常漏看通知 | 统一收件箱、重要通知推送、课程主页 |
| 研究生阿杰 | 上课、科研、兼职并行，只有碎片时间 | 跨课程作业日历、变更提醒、离线阅读 |
| 社团负责人 Mia | 关注大量活动和报名信息 | 相关性筛选、收藏与待办、原文入口 |

典型场景：

1. **周日规划一周**：阿杰打开日历视图，看到下周 4 门课的作业集中在周四和周五，已按截止时间排好；每条都附原文链接和“最后检查：10 分钟前”。
2. **截止时间被修改**：老师把一项作业的截止从周日提前到周五。系统下一次检查发现变化，更新原有事项而不是新增一条，标出“截止提前 2 天”，日历同步移动，手机收到紧急通知。
3. **跨渠道合并**：Moodle 发来的作业提醒邮件和课程页上的同一项作业被识别为同一事项，只出现一次。
4. **离线阅读与恢复同步**：Mia 在地铁上没有网络，仍能浏览缓存的通知，并把一个活动加入待办；联网后这个操作自动同步，同时补齐离线期间的新通知。
5. **再次找到信息**：两周后要报名那个活动时，Mia 在“收藏”中直接找到原通知和办理入口。
6. **课程主页**：小林打开一门课，看到未完成作业、近期通知，以及从学校官网补充的老师办公室和邮箱。

功能分三档：P0 是第 3 周必须跑通的最小可用版本，P1 是承诺交付的完整版本，P2 在 P1 完成后视进度加做。每个功能都对应一个具体的网络技术点。

| 优先级 | 功能 | 说明 | 关键网络技术 |
| --- | --- | --- | --- |
| P0 · MVP | 账号与订阅管理 | 注册登录；用校园模板一键添加 Moodle 课程、学院通知等来源，也可自定义网址和关注区域 | 自研 HTTP/1.1 网关、REST API |
| P0 · MVP | 网页采集与变化监测 | 定期检查订阅页面，识别新增、修改、删除并提取内容；也支持 RSS | 自研异步 HTTP 客户端、条件请求、超时与重试 |
| P0 · MVP | 统一收件箱 | 通知转为精简标题 + 摘要 + 原文链接；支持已读、收藏、加入待办 | REST 分页、gzip 压缩 |
| P0 · MVP | 实时推送与未读同步 | 新事项和变更即时出现在客户端；多设备同步未读状态 | 自研 WebSocket（RFC 6455） |
| P0 · MVP | 来源状态 | 每个来源显示最后成功检查时间，区分“没有更新”“检查失败”“需要重新登录” | 健康状态上报、错误分类 |

| P1 · 完整版 | 作业列表与日历 | 跨课程汇总作业，按截止时间排列；原通知修改时更新同一事项并标出变化 | 变更检测、事项版本与差异比较 |
| P1 · 完整版 | 学校邮箱接入 | 收取邮件；识别 Moodle 提醒邮件，与课程页上的同一作业合并 | 自研 IMAP 客户端（含 IDLE）、POP3、MIME |
| P1 · 完整版 | 通过平台发送邮件 | 填写收件人、主题、正文和附件，经已连接邮箱发送并查看结果 | 自研 SMTP 客户端（STARTTLS）、附件编码、防重复提交 |
| P1 · 完整版 | 离线缓存与补充同步 | 离线阅读缓存；恢复连接后补齐新增和变化，离线时的操作自动回放 | 同步游标、增量同步、幂等处理 |
| P1 · 完整版 | 相关性与优先级 | 按课程、年级、专业、关键词和截止时间打分，分级推送 | 规则引擎（见“个性化与通知分级策略”） |
| P1 · 完整版 | 截止时间抽取与变更提醒 | 识别截止时间生成日程；截止前和截止时间变化时提醒 | 定时任务 + 多通道推送 |
| P1 · 完整版 | 手机、桌面通知 | 紧急事项推送到不在线的设备 | 自研 MQTT 3.1.1 Broker（QoS 0/1） |
| P1 · 完整版 | 断线补发与故障转移 | 重连后补发错过的消息；节点宕机自动切换 | 消息序号、心跳、健康检查 |
| P1 · 完整版 | 自定义看板 | 添加、排列收件箱、列表、日历、看板等组件，保存布局和分类规则 | REST API、鉴权与用户数据隔离 |
| P2 · 加分项 | 课程与教师信息整合 | 读取课表，从学校官网补充老师办公室、电话和邮箱 | 多来源 HTTP 采集与数据关联 |
| P2 · 加分项 | 大模型摘要 | 调用大模型 API 生成更精炼的标题和摘要，失败时回退到规则提取 | HTTPS API 调用、超时降级 |
| P2 · 加分项 | 跨设备扫码传输 | 电脑生成二维码，手机扫码配对后双向传输文件 | 分块传输、断点续传、完整性校验 |
| P2 · 加分项 | 本地采集代理 | 只能在校园网内访问的来源，由本地代理采集后上传 | 代理到云端的长连接、断线重连 |
| P2 · 加分项 | 自研 DNS 解析器 | 采集引擎使用自研的异步 DNS 解析与缓存 | UDP、DNS 报文（RFC 1035） |

范围控制：P2 只在第 6 周 P1 全部完成后开始，新想法先进 P2 清单，不插队。原文提出的“校园网监测与辅助重连”不纳入本期：它需要本地程序修改网络配置并处理校园网账号，风险较高，与信息聚合主线关联也较弱。

## 系统架构

系统分为采集、业务、推送、接入四层，层与层之间用自定义二进制协议通信，每层都能独立扩展。

Flutter 客户端的 REST 请求同样经网关转发到业务服务（图中省略）；推送节点和 MQTT Broker 都只从内部总线接收消息，互不依赖。

### 模块职责

| 模块 | 职责 | 扩展方式 |
| --- | --- | --- |
| 采集引擎 | 定时检查 Moodle、学院网站、教师信息页等来源，复用登录会话，只取增量 | 按信息源哈希分片到多个采集节点 |
| 邮件服务 | 维持 IMAP IDLE 长连接接收新邮件；代用户发信；发送每日摘要 | 按用户分片 |
| 业务服务 | 去重与跨渠道合并、变更检测、规则打分、截止时间抽取、生成投递记录 | 无状态，可多实例 |
| 推送节点 | 维持 WebSocket 会话，心跳、补发与离线增量同步 | 一致性哈希，水平扩展 |
| MQTT Broker | 向不在线的设备推送紧急通知 | 单实例（课程规模足够） |
| 统一网关 | HTTPS 入口、REST 路由、WebSocket 转发、负载均衡 | 多进程 SO\_REUSEPORT |
| Flutter 客户端 | 收件箱、列表、日历、看板；本地数据库离线缓存；内置 MQTT 通知 | 一套代码发布 Web、Android、iOS、桌面端 |

### 一条通知的端到端流程

1. 调度器发现某门课的 Moodle 作业页到了检查时间，采集引擎带上该用户的会话 Cookie 和 If-None-Match 头发出 GET 请求。
2. 页面有变化，服务器返回 200；引擎提取作业列表，按“课程 + 作业链接”匹配到已有事项。
3. 采集引擎经内部总线把提取结果发给业务服务。
4. 业务服务比较新旧版本，发现截止时间从周日改为周五，写入新版本和变更记录，标记为重要变更。
5. 为每个订阅者生成投递记录，分配该用户的下一个序号 seq。
6. 分数 ≥ 80 的投递经内部总线同时发往推送节点和 MQTT Broker；40–79 分只发往推送节点。
7. 推送节点把变更编码成 WebSocket 帧，经网关送达在线的 Flutter 客户端，日历视图随即移动该作业；MQTT Broker 以 QoS 1 推送到手机，等待 PUBACK。
8. 客户端回复 ACK；若用户离线，下次连接时按 last\_seq 补发，离线期间的本地操作按幂等键回放。

## 网络编程核心技术方案

所有网络协议都从 socket 层实现；TLS 加密和邮件内容格式解析使用 Python 标准库的 ssl、email 模块（已获老师同意）。下面逐一说明九个模块要解决的网络问题和做法。

### 1. 自研 HTTP/1.1 网关

- 基于 epoll 的事件循环，非阻塞 socket；用 SO\_REUSEPORT 启动多个进程，绕开 Python GIL 的限制。
- 用状态机增量解析请求行、头部和消息体，支持 Content-Length 与 chunked 两种传输方式，正确处理 TCP 粘包和拆包。
- 支持 keep-alive 连接复用、超时回收空闲连接、限制请求头大小以防资源耗尽。
- 路由：`/api/*` 交给业务服务；`/ws` 升级为 WebSocket 并转发到推送节点；其余为 Flutter Web 构建产物等静态文件（MIME 类型、ETag、304、gzip）。
- TLS 终止：用标准库 ssl（OpenSSL）包装 socket，对外只提供 HTTPS/WSS。
- 限流：令牌桶算法，按用户和 IP 两个维度。

### 2. WebSocket 推送服务

- 握手：校验 Upgrade、Connection、Sec-WebSocket-Version 头，计算 Sec-WebSocket-Accept（Key 拼接固定 GUID 后做 SHA-1，再 Base64）。
- 帧编解码：FIN、opcode（文本、二进制、ping、pong、close）、客户端掩码、7/16/64 位三种长度编码；支持分片帧和关闭握手。
- 心跳：服务端每 25 秒发 ping，60 秒内无 pong 判定连接已断。
- 断线补发：每条消息带用户内单调递增的序号 seq。客户端重连时带上 last\_seq，服务端从数据库补发 seq 更大的消息；客户端按 seq 去重。
- 背压：某个慢客户端的发送缓冲超过阈值时，先合并、再丢弃低优先级消息，仍不行则断开，保护整个节点。

### 3. MQTT Broker（3.1.1 子集）

- 支持报文：CONNECT/CONNACK、PUBLISH、PUBACK、SUBSCRIBE/SUBACK、UNSUBSCRIBE/UNSUBACK、PINGREQ/PINGRESP、DISCONNECT。
- 实现剩余长度的变长编码、主题过滤器的 `+` 和 `#` 通配符。
- QoS 0（最多一次）用于普通通知；QoS 1（至少一次）用于紧急通知：未收到 PUBACK 就按退避重发，客户端按报文 ID 去重。
- Keep Alive：超过约定时间 1.5 倍仍无报文即断开。
- 持久会话（Clean Session = 0）：设备离线期间的 QoS 1 消息在重连后投递；每日摘要用保留消息（retained）。
- 客户端：Flutter 客户端内置 MQTT 连接（mqtt\_client 库），收到紧急通知后弹出系统通知；另用 mosquitto\_pub/sub 等标准客户端做互通测试，证明自研 Broker 符合标准。移动端后台限制：Android 用前台服务保持连接；iOS 不允许应用在后台长期保持连接，依靠持久会话在重新打开应用时立即收到离线期间的 QoS 1 消息。

### 4. 邮件模块：IMAP、SMTP、POP3 客户端

- IMAP over TLS（993 端口）：LOGIN 或 AUTHENTICATE XOAUTH2，SELECT 收件箱，UID SEARCH 找新邮件，UID FETCH 拉取头部与正文（使用 BODY.PEEK，不改变用户的已读状态）。
- IDLE（RFC 2177）：保持长连接，等待服务器主动通知新邮件，实现秒级到达；按 RFC 建议每 29 分钟重新发起一次 IDLE，避免被服务器超时断开。
- 增量同步：记录 UIDVALIDITY 和已处理的最大 UID，断线重连后只拉取增量。
- MIME 处理：用 email 模块解析多层 multipart、Base64 与 Quoted-Printable、RFC 2047 编码的中文标题；识别 Moodle 发出的作业提醒邮件，交给业务服务与课程页上的同一事项合并。
- SMTP 发信（587 端口）：EHLO → STARTTLS → AUTH → MAIL FROM → RCPT TO → DATA，实现点号转义；附件按 MIME multipart 组装并 Base64 编码；遇到 4xx 临时错误按退避重试。
- 防重复提交：每次发信带客户端生成的幂等键，并写入唯一的 Message-ID；同一幂等键重复提交时直接返回上次结果，不会发出第二封。
- POP3（995 端口）：作为不支持 IMAP 的邮箱的兼容方案，实现 USER/PASS、STAT、UIDL、RETR。

### 5. 高并发采集引擎

- 调度：最小堆按“下次检查时间”排序；检查周期按信息源的更新频率自适应，常更新的源几分钟一次，冷门源一小时一次。
- 事件驱动：asyncio 加自研 HTTP/1.1 客户端，不使用 requests、aiohttp 等现成 HTTP 库。
- 连接池：按主机复用 keep-alive 连接；设置每主机并发上限和全局并发上限。
- 条件请求：保存每个源的 ETag 和 Last-Modified，下次请求带 If-None-Match / If-Modified-Since；内容未变时服务器返回 304，不传正文。
- 超时与重试：连接超时和读取超时分开设置；失败按指数退避加随机抖动重试；连续失败的源进入熔断，不拖累其他源。
- 礼貌抓取：遵守 robots.txt，按主机限速，设置可识别的 User-Agent；请求带 `Accept-Encoding: gzip`。
- 去重：对“来源 + 链接 + 标题”计算哈希，重复内容不入库。

### 6. 内部二进制协议（节点间消息总线）

采集服务、业务服务、推送节点和 MQTT Broker 之间，用自定义的 TCP 二进制协议通信，而不是直接使用 Redis 等现成中间件。帧格式如下：

| 字段 | 长度 | 说明 |
| --- | --- | --- |
| Magic | 2 字节 | 固定为 0x474C（“GL”，Gleaner 的缩写），快速识别非法数据流 |
| Version | 1 字节 | 协议版本号 |
| Type | 1 字节 | PUBLISH、ACK、HEARTBEAT、NODE\_JOIN、NODE\_LEAVE、SUBSCRIBE |
| Flags | 1 字节 | 是否压缩、是否需要确认 |
| Seq | 4 字节 | 发送方序号，用于确认和去重 |
| Length | 4 字节 | Payload 长度，用于帧定界 |
| Payload | N 字节 | MessagePack 编码的消息体 |
| CRC32 | 4 字节 | 整帧校验（不含 CRC 字段本身） |

- 用长度前缀定界，解决粘包和拆包；校验失败立即断开并重连。
- 需要确认的消息若超时未收到 ACK 就重发，接收方按“节点 + Seq”去重，实现至少一次投递。
- 每 5 秒发送一次 HEARTBEAT，15 秒收不到心跳即视为对端下线。

### 7. 负载均衡、健康检查与故障转移

- 网关把 WebSocket 连接分配到多个推送节点：按用户 ID 做一致性哈希（带虚拟节点），同一用户的多个连接落在同一节点，便于多端同步。
- 主动健康检查：网关每 5 秒探测各节点（TCP 连接 + `/health`），连续 3 次失败即摘除，恢复后自动加回。
- 被动健康检查：转发失败计数超过阈值时临时摘除节点。
- 采集任务调度：多个采集节点向调度器发送心跳，调度器把信息源分配给存活节点；某个节点 15 秒无心跳，其任务自动重新分配，支撑多用户、多信息源同时运行。
  （实现说明：心跳由总线 Hub 汇总并广播存活节点列表，各采集节点用一致性哈希自行认领来源，不设集中调度器；见 docs/decisions.md 第 3 条。）
- 故障转移：节点宕机 → 其上的连接断开 → 客户端指数退避重连 → 网关按哈希环把用户映射到下一个节点 → 客户端带 last\_seq 补发 → 用户无感恢复。

### 8. 会话管理与变更检测

- 会话复用：用户在平台内完成一次来源登录，服务端加密保存 Cookie 或 Token，采集时自动附带。
- 失效识别：遇到跳转到登录页、401 或 403 等信号，判定会话失效，把来源标为“需要重新登录”并通知用户，不再反复请求。
- 优先官方接口：如果本校 Moodle 开放了 Web 服务或日历导出（iCal），优先使用，降低页面解析的脆弱性。
- 事项身份：每个事项按“来源 + 稳定标识（如作业链接）”建立身份；每次提取生成字段快照，与上一版本逐字段比较，得出新增、修改、删除。
- 重要变更：截止时间提前、附件替换、提交要求变化被标为重要变更并触发推送；仅措辞调整只记入历史，不打扰用户。
- 状态表达：区分“检查成功、没有更新”“检查失败（网络、超时、解析错误）”“需要重新登录”，并显示最后一次成功检查的时间，让学生判断信息是否可靠。

### 9. 离线缓存与增量同步

- 客户端缓存：Flutter 客户端用本地数据库（drift 库；手机和桌面端基于 SQLite，Web 端基于 IndexedDB）保存收件箱、作业和日历数据，离线时照常浏览。
- 同步游标：每个用户的投递都带单调递增的 seq。客户端保存最后同步到的 seq，恢复连接后通过 `GET /api/sync?cursor=<seq>` 或 WebSocket 的 hello 消息取回期间的新增和变更。
- 离线操作回放：离线时的已读、收藏、加入待办写入本地操作队列，每个操作带唯一的幂等键；联网后按顺序回放，服务端按幂等键去重，重复提交不会产生副作用。
- 冲突处理：个人状态以最后修改时间为准，来源内容以服务端最新版本为准。
- 完整性说明：服务端在用户离线时继续采集，所以客户端离线不会漏掉信息；但如果来源在两次检查之间新增又删除了内容，系统无法找回，界面会如实显示最后检查时间。

| 主题 | QoS | 内容 |
| --- | --- | --- |
| gleaner/u/{uid}/urgent | 1 | 紧急通知与重要变更 |

## 个性化与通知分级策略

我们用可解释的规则打分，而不是黑盒推荐：每条信息对每个用户得到一个 0–100 的优先级分，分数决定走哪条推送通道。

### 优先级打分

```latex
\text{score} = 100 \times \left(0.30\,S_{\text{source}} + 0.25\,S_{\text{keyword}} + 0.25\,S_{\text{deadline}} + 0.20\,S_{\text{match}}\right)
```

各项取值都在 0 到 1 之间：

- S\_source：来源权重，例如必修课的 Moodle 页面 1.0、学院活动 0.4；白名单发件人视为 1。
- S\_keyword：命中关键词规则的程度，默认关键词包括“截止、deadline、考试、调课、取消”，用户可自定义加分词和屏蔽词。
- S\_deadline：离截止时间越近越高，24 小时内为 1，7 天以外为 0。
- S\_match：与用户课程、年级、专业的匹配程度；通知写明“面向大三计算机专业”而用户正好符合时为 1，明确不符合时为 0，未注明时取中间值。

权重是初始值。用户对某条信息点“不重要”时，会降低对应来源或关键词的权重，系统逐步贴合个人习惯。

### 分级推送

| 等级 | 分数 | 推送方式 |
| --- | --- | --- |
| 紧急 | ≥ 80 | 客户端即时推送 + MQTT（QoS 1）系统通知到手机和桌面 |
| 普通 | 40–79 | 只推送到打开的客户端界面，不弹系统通知 |
| 低 | < 40 | 不推送，进入信息流和每日摘要 |

免打扰时段（默认 23:00–7:00）只放行紧急通知，其余积压到早上的摘要中。

重要变更（截止时间提前、附件替换、提交要求变化）至少按普通级推送；如果距截止不足 7 天，按紧急级推送。

### 截止时间抽取

- 用规则和正则识别中英文日期时间，例如“10月30日23:59前”“本周五前”“due Oct 30, 11:59 PM”“2026-10-30”。
- “下周三”这类相对日期，按信息的发布时间换算成具体日期。
- 识别结果写入 items.deadline\_at，在截止前 24 小时和 2 小时各提醒一次。
- 界面上可以一键修正识别结果，修正记录用于改进规则。
- 可选扩展：调用大模型 API 提升识别准确率，但不作为核心交付，避免稀释网络编程主线。

### 精简标题与摘要

- 规则提取（P0）：去掉标题中的课程代码和“关于”“通知”等冗余词；摘要取正文前两句，并抽出日期、地点和适用对象。
- 大模型生成（P2）：调用大模型 API 生成一句话标题和三行摘要；超时或失败时回退到规则结果。
- 每条消息都保留原文链接、来源名称和最后检查时间；摘要只是导读，不替代原文。

## 测试与评估方案

评估回答四个问题：协议实现是否正确，性能是否达标，出故障时是否可靠，真实用户是否在用。

### 协议一致性与互通

| 协议 | 测试方法 |
| --- | --- |
| HTTP/1.1 | 浏览器、curl、wrk 访问；单元测试覆盖 chunked、keep-alive、畸形请求 |
| WebSocket | Autobahn Testsuite 一致性测试套件；主流浏览器和 Flutter 客户端实测 |
| MQTT | 用标准客户端（mosquitto\_pub/sub、paho-mqtt）和 Flutter 客户端与自研 Broker 互通 |
| IMAP、SMTP、POP3 | 先连本地 Dovecot + Postfix 测试服务器，再对接真实学校邮箱 |
| 内部二进制协议 | 单元测试 + 模糊测试：随机截断、篡改 CRC、分段到达 |
| 全部协议 | Wireshark 抓包，截图放入报告并逐字段标注 |

### 性能指标（目标值）

| 指标 | 目标 |
| --- | --- |
| 单推送节点并发 WebSocket 连接 | ≥ 5,000 |
| 推送延迟（入库到客户端收到）P99 | < 1 秒 |
| 变更送达时间（来源修改到用户收到） | ≤ 一个检查周期 + 5 秒 |
| 截止时间抽取准确率（本校 Moodle 与学院通知样本） | ≥ 90% |
| 网关 REST API 吞吐（2 核，缓存命中） | ≥ 1,000 请求/秒 |
| 采集引擎吞吐 | ≥ 300 个源/分钟 |
| 条件请求节省的流量 | ≥ 70% |
| 推送节点宕机后客户端恢复时间 | < 10 秒，消息零丢失 |

### 对比实验

对比实验是报告的核心素材，每组都给出图表和分析：

1. select 与 epoll：连接数从 500 增加到 5,000 时，CPU 占用和延迟的变化。
2. 有无连接池与 keep-alive：抓取同一批源的耗时和 TCP 握手次数。
3. 有无条件请求：一天内的总流量与 304 响应占比。
4. MQTT QoS 0 与 QoS 1：吞吐量，以及在丢包环境下的送达率。
5. 单节点与三节点：最大连接数和延迟，验证水平扩展效果。

### 故障注入

- 用 tc netem 模拟延迟、丢包和乱序，验证重传、补发和去重逻辑。
- 运行中直接结束一个推送节点或采集节点进程，测量恢复时间、丢失消息数和任务重新分配时间。
- 让某个信息源持续超时或返回登录页，验证退避、熔断和“需要重新登录”提示，确认不影响其他源。
- 断网测试：客户端断网期间在服务端制造新增和修改，并在客户端做已读、收藏操作；联网后核对补齐结果，以及每个操作是否恰好生效一次。

### 真实用户指标

统计注册用户数、日活跃用户、人均订阅源数、推送点击率和“不重要”标记比例；学期末发放 SUS 可用性问卷。

### 用户验证与竞品对比

竞品分析中的三个设计目标要用数据证明。邀请 5–8 名同学完成同一项真实任务——周日晚上整理下一周的作业和相关通知，分别使用原有方式（Moodle + 邮箱 + 手动日历）、Distill 和拾课，记录完成时间、操作步骤数和遗漏项数。

如果某项需求现有工具已充分满足，就收缩对应功能，把精力放在跨来源整合仍然困难的部分。

## 部署与运维

服务在第 6 周上线，部署一条命令完成，监控面板既用于日常运维，也用于现场演示。

- 环境：一台 2 核 4 GB 云服务器起步，压测时临时扩到 2–3 台；绑定域名，使用 Let's Encrypt 证书。
- 编排：Docker Compose 一键启动网关、2 个推送节点、采集服务、邮件服务、MQTT Broker、PostgreSQL、Prometheus 和 Grafana。
- 持续集成：代码托管在 GitHub，每次提交由 GitHub Actions 运行单元测试和协议测试，并构建 Flutter 各端产物；合并到 main 后自动部署。
- 客户端发布：Flutter Web 版由网关分发，扫码即用；Android 提供 APK 下载；Windows、macOS 提供安装包；iOS 视情况通过 TestFlight 内测（需要 Apple 开发者账号）。
- 监控：各服务暴露 /metrics，指标包括在线连接数、每秒消息数、推送延迟分布、抓取成功率、304 占比。
- 告警：节点下线或抓取失败率过高时发邮件告警，复用自研 SMTP 模块。
- 日志与备份：结构化日志集中收集；数据库每日备份。
- 上线节奏：先邀请组员和好友约 10 人内测，修复问题后向同班和学院同学开放。

## 安全、隐私与合规

用户会把学校邮箱等授权交给我们，所以隐私保护是上线的前提，而不是附加项。

- 最少授权：优先使用官方接口、OAuth2 或应用专用密码；能公开获取的来源不要求登录。
- 会话凭据：登录 Cookie 和 Token 与密码同等对待，加密保存，过期即删；平台不保存学校统一认证的密码。
- 加密保存：授权信息用 AES-GCM 加密存储，密钥只存在服务器环境变量中；用户密码用 bcrypt 或 argon2 哈希。
- 传输加密：全站 HTTPS/WSS；MQTT 走 TLS（8883 端口）；IMAP、SMTP 走 TLS。
- 数据最少化：邮件只保存标题、发件人、摘要和链接，不长期保存正文和附件；用户可一键删除账号与全部数据。
- 访问控制：API 鉴权、用户数据隔离、MQTT 主题访问控制，令牌桶限流防止滥用。
- 内容安全：采集到的 HTML 统一清洗后再展示，防止 XSS 攻击。
- 礼貌抓取：遵守 robots.txt、网站使用条款和学校信息系统使用规定，按主机限速；不绕过验证码。
- 知情同意：注册页提供隐私说明，写明收集哪些数据、如何使用、如何删除。

每人负责一个从 socket 层自研的协议模块，另外承担一项跨模块职责。这样每个人的贡献都有清晰的代码、文档和汇报内容作为依据。

| --- | --- | --- | --- | --- |
| A（组长） | 统一网关 | HTTP/1.1 服务端、TLS、路由、限流、负载均衡与健康检查、采集节点调度（去中心化分配，见 docs/decisions.md 第 3 条） | 2、4、5 | 项目管理、整体架构、部署与 CI |

| C | 采集引擎 | 自研 HTTP 客户端、调度、连接池、条件请求、会话管理、变更检测，Moodle/学院网站/教师信息采集模板 | 2、4 | 测试负责人：CI 测试与故障注入 |

- 每个模块写一份协议设计文档，最终汇编进报告；汇报时每人讲解自己的模块。

## 风险与应对

最大的风险是范围失控，其次是校园系统的访问限制（Moodle、学校邮箱不配合）。每项风险都准备了不影响主线交付的备选方案。

| 风险 | 可能性 | 影响 | 应对 |
| --- | --- | --- | --- |
| 范围失控，功能做不完 | 高 | 高 | 严格按 P0/P1/P2 推进；第 3 周 MVP 关口；P2 只在 P1 完成后开始 |
| Moodle 只能在校园网访问或需统一认证，云端无法采集 | 中 | 高 | 第 1 周实测；优先使用 Moodle Web 服务、日历导出（iCal）或提醒邮件；必要时启用本地采集代理（P2） |
| 现场演示失败 | 中 | 高 | 前一天在教室全流程彩排；手机热点备用网络；本地备用环境；录制备份视频 |
| 隐私或安全事故 | 低 | 高 | 执行“安全、隐私与合规”各项措施；上线前组内安全自查 |
| 竞品已覆盖核心能力，差异化不明显 | 中 | 中 | 第 2 周起用真实场景做对比测试（见“用户验证与竞品对比”），聚焦作业变更跟随与跨渠道合并 |
| 学校邮箱要求 OAuth2 或禁止第三方登录 | 中 | 中 | 第 1 周先验证；不行则让用户把邮件自动转发到拾课收件地址，由自研 SMTP 接收端处理 |
| 页面结构变化导致解析失败 | 中 | 中 | 解析规则集中维护并版本化；解析失败时明确显示“检查失败”，不静默丢数据 |
| Flutter 多平台适配耗时，移动端后台受限 | 中 | 中 | 以 Flutter Web 和 Android 为主要交付，桌面与 iOS 视进度；iOS 后台通知依靠 MQTT 持久会话，打开应用时补收 |
| 自研 MQTT Broker 进度落后 | 中 | 中 | 接口与 Mosquitto 兼容，必要时临时替换，先保证端到端可用 |
| 组员时间冲突（兼职、科研、其他课程） | 中 | 中 | 模块解耦，接口先冻结，用 mock 并行开发；每个模块有后备成员 |
| 上线后真实用户少 | 中 | 中 | 先邀请同班同学和社团试用；校园模板让新用户一分钟内完成接入 |
| Python 性能不达标 | 中 | 低 | 多进程加 SO\_REUSEPORT 水平扩展；瓶颈分析本身写入报告 |

## 演示方案

演示围绕三个现场时刻设计，让同学亲身参与，时长按老师要求安排。

1. **扫码加入**：投屏二维码，请现场同学用手机打开 Flutter Web 版（无需安装）注册，并用校园模板订阅测试课程；大屏上的 Grafana 面板实时显示在线连接数上升。
2. **作业变更秒级送达**：组员在测试课程页把一项作业的截止时间提前。同学工作台上的该事项标出“截止提前”，日历同步移动，手机收到紧急通知；同时用 Wireshark 展示 WebSocket 帧和 MQTT 的 PUBLISH/PUBACK 交互。
3. **断网与故障恢复**：断开演示电脑的网络，工作台仍可浏览缓存，并在离线时把一条通知加入待办；同时当场结束一个推送节点进程。恢复网络后，客户端自动重连到其他节点，补齐新消息，待办操作只生效一次。

之后展示预先录制的 5,000 连接压测过程和对比实验图表，再由每位成员用约 1 分钟讲解自己负责的模块。

演示准备：

- 测试课程页由我们自己托管，结构仿照本校 Moodle 作业页，不依赖真实课程的更新时间。
- 演示前一天在教室网络环境下完整彩排；准备手机热点作为备用网络。
- 三个现场时刻全部录制备份视频，现场出问题时立即切换。
